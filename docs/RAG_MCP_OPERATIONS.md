# RUSA-AI local RAG and MCP operations

The knowledge retrieval stack is an optional, separately deployed service. It is
isolated from the core inference API and autonomous worker unless explicitly
configured. The production path supports local embeddings through Ollama; an
OpenAI-compatible HTTPS provider remains available for deployments that choose
a managed embedding endpoint.

## Architecture and guarantees

- PostgreSQL 16 with pgvector stores documents, chunks, collection embedding
  profiles, HNSW vector indexes, and full-text search vectors.
- Retrieval combines semantic and lexical candidates using weighted
  Reciprocal Rank Fusion. Tune `RUSA_RAG_VECTOR_WEIGHT`,
  `RUSA_RAG_LEXICAL_WEIGHT`, and `RUSA_RAG_HNSW_EF_SEARCH`.
- Forced row-level security is applied to every tenant-owned knowledge table.
  The application assumes the non-login `rusa_knowledge_worker` role inside
  each tenant-scoped transaction.
- Collection embedding profiles prevent accidental comparison of vectors
  generated by different models. A collection is pinned to one provider,
  model, native dimension, and stored dimension. To change models, use a new
  collection or perform a controlled full re-embedding.
- MCP exposes read-only retrieval tools. Tenant identity is derived from a
  hashed bearer-token registry; the caller cannot pass or override tenant IDs.
- Retrieved document text is untrusted evidence, not executable instructions.
  Credential-like material is rejected before embedding and again before
  returning legacy retrieved content.

## Runtime requirements

- Python 3.11 or newer.
- PostgreSQL 16 with the pgvector extension.
- Apply migrations in order:
  1. `migrations/007_rag_knowledge_pgvector.sql`
  2. `migrations/008_rag_embedding_profiles.sql`
- The MCP service requires a SHA-256 tenant-token registry in
  `RUSA_MCP_TENANT_KEYS`. Store token digests, never raw bearer tokens.
- The local default embedding model is `bge-m3` served by Ollama. Its native
  1024-dimensional vectors are zero-padded to the existing 1536-dimensional
  pgvector column. Appending zero coordinates preserves dot products, vector
  norms, and cosine similarity; it does not change or compress the model
  embedding. The native and stored dimensions are recorded in each collection
  profile.

## Start a complete local RAG and MCP stack

The local Compose file creates an isolated pgvector database, Ollama runtime,
one-shot model pull, and authenticated MCP service. It publishes MCP only on
loopback. Ollama and PostgreSQL are not published to the host.

Create local secrets in the same shell session:

```bash
export RUSA_RAG_ADMIN_PASSWORD="$(openssl rand -hex 32)"
export RUSA_RAG_DB_PASSWORD="$(openssl rand -hex 32)"
export RUSA_MCP_TOKEN="$(openssl rand -hex 32)"
export RUSA_MCP_TENANT_KEYS="$(python -c 'import hashlib,json,os; print(json.dumps({hashlib.sha256(os.environ["RUSA_MCP_TOKEN"].encode()).hexdigest():"tenant-a"}))')"
mkdir -p knowledge-input
```

Start the stack:

```bash
docker compose -f docker-compose.rag-local.yml up --build -d
docker compose -f docker-compose.rag-local.yml ps
docker compose -f docker-compose.rag-local.yml exec rag-mcp rusa-knowledge check
```

The first start downloads `bge-m3` into the persistent Ollama volume. The
default profile is CPU-based. For GPU acceleration, use a host-specific Compose
override with the supported NVIDIA Container Toolkit or equivalent device
configuration. Pin `RUSA_OLLAMA_IMAGE` to an immutable digest when using this
stack beyond local development.

The MCP endpoint is:

- Streamable HTTP: `http://127.0.0.1:8002/mcp`
- Liveness: `http://127.0.0.1:8002/health/live`
- Readiness: `http://127.0.0.1:8002/health/ready`

Use `RUSA_MCP_TOKEN` as the bearer token for the `tenant-a` MCP connection.
The token itself is not stored in the container registry; only its lowercase
SHA-256 digest is configured. The existing `.vscode/mcp.json` can connect to
the endpoint by entering the URL and token when prompted.

## Ingest local documents

Place source files under `knowledge-input/`. The directory is mounted read-only
inside the service container. Supported formats are TXT, Markdown, HTML, PDF,
and DOCX.

```bash
docker compose -f docker-compose.rag-local.yml run --rm \
  --entrypoint rusa-knowledge rag-mcp ingest \
  --file /data/knowledge/handbook.pdf \
  --tenant-id tenant-a \
  --collection agent
```

Check service and database readiness:

```bash
docker compose -f docker-compose.rag-local.yml exec rag-mcp rusa-knowledge check
```

## Ingest large Parquet telemetry out-of-core

The `ingest-parquet` command uses DuckDB to scan and aggregate Parquet data
without loading the raw file into a Pandas DataFrame. It groups records by one
timestamp bucket and one group column, then writes bounded JSON summary
documents into RAG. Each summary includes row count and per-metric average,
maximum, standard deviation, and approximate P95.

Example for a DevOps telemetry file:

```bash
docker compose -f docker-compose.rag-local.yml run --rm \
  --entrypoint rusa-knowledge rag-mcp ingest-parquet \
  --file /data/knowledge/devops_1B.parquet \
  --tenant-id tenant-a \
  --collection devops \
  --timestamp-column ts \
  --group-column service \
  --metric-columns cpu_percent,memory_percent,network_in,network_out \
  --bucket-minutes 5 \
  --rows-per-document 100 \
  --max-documents 10000 \
  --memory-limit 4GB \
  --threads 4 \
  --temp-directory /tmp/duckdb \
  --dry-run
```

Review the aggregate count and sample first. Remove `--dry-run` to embed and
index the summaries. The default cap is 10,000 documents; each document can
contain at most 500 aggregate rows. Increase the cap deliberately after
reviewing expected index size, disk capacity, and embedding throughput.

This pipeline can scan very large files, including billion-row Parquet files,
but completion time depends on storage throughput, group cardinality, available
temporary disk, and CPU. It indexes grouped summaries rather than one vector
per raw event. A high-cardinality group-by can still produce a very large
result set; the document cap is a safety control, not a throughput guarantee.

Column names must be simple SQL identifiers. The timestamp column must have a
DATE or TIMESTAMP type, and metric columns must be numeric. For multiple group
dimensions, materialize a stable composite group column upstream before
ingestion.

## Embedding and retrieval configuration

`KnowledgeService.from_env()` supports:

| Variable | Local default / meaning |
|---|---|
| `RUSA_EMBEDDING_PROVIDER` | `ollama` in local Compose; `openai-compatible` otherwise |
| `RUSA_EMBEDDING_BASE_URL` | `http://ollama:11434` for local Ollama |
| `RUSA_EMBEDDING_ALLOWED_HOSTS` | Explicit allowlist for trusted internal HTTP hosts |
| `RUSA_EMBEDDING_MODEL` | `bge-m3` |
| `RUSA_EMBEDDING_NATIVE_DIMENSIONS` | `1024` for `bge-m3` |
| `RUSA_EMBEDDING_TIMEOUT` | Request timeout in seconds |
| `RUSA_EMBEDDING_MAX_RETRIES` | Bounded retry count for transient transport/HTTP failures |
| `RUSA_RAG_VECTOR_WEIGHT` | Semantic retrieval weight; default `0.7` |
| `RUSA_RAG_LEXICAL_WEIGHT` | Full-text retrieval weight; default `0.3` |
| `RUSA_RAG_HNSW_EF_SEARCH` | HNSW search breadth; default `80` |
| `RUSA_KNOWLEDGE_DB_POOL_MIN` | PostgreSQL pool minimum |
| `RUSA_KNOWLEDGE_DB_POOL_MAX` | PostgreSQL pool maximum |

Weights are normalized before retrieval and must be finite, non-negative, and
not both zero. HNSW `ef_search` is bounded from 1 to 1000. Increasing candidate
breadth and HNSW search breadth can improve recall at the cost of query latency.

Do not mix embedding models in one collection. Migration 008 marks existing
unversioned collections as legacy. Reindex them into a new collection before
switching the serving model. The store rejects ingestion or search when the
configured collection profile does not match the active embedding profile.

## Production deployment

The production Compose stack expects immutable image digests for both
`RUSA_RAG_MCP_IMAGE` and `RUSA_OLLAMA_IMAGE`, plus a restricted PostgreSQL
login DSN and tenant token digest registry.

1. Create a dedicated login role such as `rusa_rag_runtime` with
   `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOINHERIT`.
2. Apply migrations 007 and 008 as a database owner. Migration 008 grants
   `rusa_knowledge_worker` to an existing `rusa_rag_runtime` login with
   `INHERIT FALSE`; the connection explicitly assumes that role per
   transaction.
3. Set `RUSA_KNOWLEDGE_DATABASE_URL` to the restricted login DSN. Use
   `sslmode=verify-full` for a remote PostgreSQL service and a trusted CA.
4. Set `RUSA_MCP_TENANT_KEYS` to a JSON object mapping SHA-256 token digests
   to tenant IDs. Do not put raw tokens in environment registries or logs.
5. Set `RUSA_RAG_MCP_IMAGE` and `RUSA_OLLAMA_IMAGE` to immutable image
   digests, preload `bge-m3` in the Ollama persistent volume, and start the
   `ollama` and `rag-mcp` services.
6. Terminate TLS at a trusted ingress or reverse proxy. The MCP listener binds
   to host loopback and must not be exposed directly to the public internet.

The RAG/MCP container runs as an unprivileged user with a read-only application
filesystem, dropped Linux capabilities, bounded process count, and a bounded
temporary filesystem. Ollama is reachable only on the internal Compose network.
The MCP application rate limiter is per process; use an ingress/API gateway
limit as well when deploying multiple replicas.

For controlled model upgrades, deploy the new model into a new collection,
re-embed and evaluate it, then switch consumers after retrieval evaluation.
Do not silently overwrite the active collection profile.

## Autonomous worker retrieval integration

Build the worker image with:

```bash
docker build --build-arg RUSA_INSTALL_RAG=1 -f Dockerfile.worker .
```

Set `RUSA_RAG_ENABLED=true` on the worker only after migrations and grants are
verified. Configure the worker with the same embedding provider, model, and
collection profile as the MCP service. For local Ollama, the worker must share
a private network with the Ollama service and use
`RUSA_EMBEDDING_BASE_URL=http://ollama:11434` plus
`RUSA_EMBEDDING_ALLOWED_HOSTS=ollama`.

The task tenant is derived from the authenticated queue lease and injected into
the read-only worker retrieval tools. The model cannot supply or override
`tenant_id`. The worker uses its restricted database login and explicitly
assumes the non-login `rusa_knowledge_worker` role for each knowledge-store
transaction.

## Operational boundaries

- MCP exposes read-only retrieval tools: `search_knowledge`,
  `get_document`, and `list_collections`. Document ingestion is an operator
  CLI operation, not an agent tool.
- Do not expose MCP publicly without TLS, ingress authentication, and network
  policy.
- Do not enable plain HTTP except for loopback or explicitly trusted internal
  hosts.
- Do not log bearer tokens, raw credentials, or full retrieved document bodies.
- Keep raw telemetry in its governed data lake; index bounded aggregates and
  summaries in RAG.
- Run retrieval evaluation against curated relevance datasets before changing
  chunking, embedding models, or hybrid retrieval weights.
- Monitor database pool saturation, Ollama model memory, ingestion backlog,
  HNSW index size, query latency, and retrieval Recall@K/MRR/NDCG.
